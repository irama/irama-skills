name: cleanup
description: Find every git worktree on this machine, sort it into Running, Pruned, Ready to push and Abandoned, auto-prune the safe ones, and deliver one brief of the decisions. Park, delete and hold run from the returned brief; push, merge and resume run from the returned brief. Use when the user says "cleanup", "find all my worktrees", "tidy my worktrees", or invokes /cleanup.

`/cleanup` walks every repo under the home folder and returns **one brief** with four groups. Spec: `docs/specs/cleanup.md`. Decision record: `docs/adr/0001-cleanup-acts-on-the-returned-brief.md`.

**This build auto-prunes, then applies the returned brief (park, delete, hold, push, merge, resume).**

`<skill-dir>` is the folder this skill loaded from. `REG` is the conductor script, `<skill-dir>/../threads/assets/register.py`.

## `/cleanup`

1. **Take the claim.** Run `python3 REG claim cleanup:run --note "cleanup run <run-id>"`. Go on only if the output starts with `claimed`. `HELD by …` means another live run has it, and `not claiming` (exit 0) means this thread has no identity record: in both cases stop and say the line.
2. **Make the run folder.** Run id `<YYYY-MM-DD-HHMM>` (`date +%Y-%m-%d-%H%M`); folder `~/.claude/cleanup/<run-id>/`. Everything this run writes goes there, outside every repo.
3. **Discover and classify.** `python3 <skill-dir>/discover.py > <dir>/discover.json` (about 15 s; read-only except one fetch per repo).
3b. **Auto-prune.** `python3 <skill-dir>/prune_auto.py <dir>/discover.json --self-cwd <this worktree>`. Each Pruned candidate is re-classified just before removal, its dev server is stopped (`localhost-dev.sh kill-repo`), then it goes through `orca worktree rm --delete-branch` (Orca rows, closing the chat card) or `git worktree remove` and `git branch -d` (never `-D`). The remote branch is deleted only when its current tip is an ancestor of `origin/<default>`. A failed removal becomes an Abandoned row with the error; a worktree that went live meanwhile is left alone. It rewrites `discover.json`, so the next step reports real removals. `--dry-run` prints what would be removed and changes nothing.
4. **Write the template rows.** `python3 <skill-dir>/make_brief.py rows <dir>/discover.json --run-dir <dir>`. This writes `rows.json` (Running, Pruned, push rows with their recommendation) and one `abandoned/<key>.prompt.md` per Abandoned row, holding exactly the spec's inputs: the diff against the merge base (capped at 400 lines, by-file summary beyond), the commit log, handoffs and closing notes that name it, and the first user and last assistant message of the session that entered it (2,000 characters each).
5. **Write the Abandoned rows.** For each prompt file, start one subagent with `model: sonnet`, in parallel batches of up to 8, prompt: `Read <prompt path> and do exactly what it says. Return budget: 12 lines.` Each writes `abandoned/<key>.answer.md`. A missing or malformed answer is not retried: the brief falls back to the facts for that row. Never read the answers into this thread beyond the 12 returned lines.
6. **Build the brief.** `python3 <skill-dir>/make_brief.py brief <dir>/rows.json --read-only --render`. (`--read-only` now only means "the brief's decisions are not acted on"; the Pruned group reports real removals.) It writes `cleanup.md`, builds `cleanup.html` with peakstate-brief's `build-brief.mjs` and runs `brief-lint.py`. A non-zero exit is a lint defect: fix the generator, never the HTML.
7. **Deliver.** Start `~/.claude/bin/brief-deliver <dir>/cleanup.html` in the background (read `~/.claude/docs/brief-delivery.md` first) and give the `file://` link. When it exits 0, the responses file it names is the approval, row by row.
7b. **Apply.** `python3 <skill-dir>/apply.py <dir> <responses.json> --self-cwd <this worktree>`. A row absent from the responses takes its recommendation; `none` does nothing; two ticks do nothing and ask. Before each row it re-checks the tip, the cleanliness and liveness, and on a mismatch does nothing and writes an ask. Order: parks, deletes, merges, resumes, pushes now, deferred pushes. Park writes `~/.claude/cleanup/parked.json` (30 days, ends early if the tip moves, comes back marked 'park expired'). Delete tags the tip `cleanup/deleted/<branch>-<YYYYMMDD>` (local; stops if it exists), moves `.env*`, `*.pem`, `*.key`, `credentials*`, `.npmrc` to `~/.claude/cleanup/<run-id>/kept/<repo>/<worktree>/` (mode 600), then removes the worktree and branch; it refuses a parent of nested worktrees, and the result round carries the undo command. The script writes `results.json`, rebuilds the brief as round two (same `brief-id`, fresh `consumed:`, answered rows become `## Your Qn answer: ...`), runs `brief-lint.py` and `check-coverage.py`, and writes `asks.json`. A non-zero exit is a defect to fix, not to skip.
7b2a. **Headless runs.** `/push` and `/merge` run as `claude -p --permission-mode bypassPermissions <prompt>` in their own process group (nobody can answer a prompt). The `/push` prompt carries the exact expected tip and the approved SHA list, and tells the session to stop with `CLEANUP-RESULT: refused <reason>` if `git rev-list origin/<default>..<default>` differs in any way; it ends with `CLEANUP-RESULT: pushed <sha>`. `ship.py` reads only that marker line: a missing marker is a failure even at exit 0, and `/merge` output that stops, asks or reports a finding counts as refused even if `<default>` moved (the moved range is reported and nothing is pushed). After `/push`, `git ls-remote` must show the approved tip; any other remote tip is an ALARM naming the unapproved commits, never a success. On timeout the whole process group is killed and the result says "timed out, state unknown, check migrations". `/push` may apply migrations before it fails, so every failed or timed-out push result tells the owner to check migrations.
7b2. **Shipping rows** (`ship.py`, called by `apply.py`). The returned brief counts as invoking `/push` for that repo and that commit range only. *Push now*: fetch, then compare `origin/<default>..<default>` with the commits the row listed; identical (or a subset) runs the `/push` steps with that repo's folder as the working directory, and any extra commit pushes nothing and writes an ask. A repo whose main checkout is not on `<default>` is skipped with a reason. *Merge and push*: record `<default>`'s tip before and after `/merge`'s steps (it squashes, so the SHA is new); the repo's approved range becomes the shown range plus exactly that span, only if the merge's commits all come from that branch. A push row set to Hold does not approve its commits for a merge's push. One push per repo. After a successful push the repo's Ready worktrees go through `prune_auto.py`. *Push when the running work lands* (always its own watcher, even when the repo also has a merge row; only Push now approves the shown range for an immediate push): `apply.py` writes `deferred.json` and the row's result says `waiting`. For each waiting row, start the Monitor tool (24 h limit, persistent off) on the command in the result text, `python3 <skill-dir>/ship.py deferred <dir> <row key> --self-cwd <this worktree>`. It polls every 60 s until none of the named worktrees reads Running, then checks the named branches are on local `<default>` (ancestor, `git cherry`, or a squash with the same files) and pushes only if every extra commit is one of that work's own commits (reachable from its tip, not from the default tip recorded at approval) or the merge commit that landed them; otherwise, or at 24 h, it writes an ask. It updates `results.json`, prunes Ready worktrees on success and rebuilds round two; re-run 7c and 7d when it exits. The Monitor blocks nothing: deliver round two first with the push shown as waiting.
7b3. **Resume rows** (`resume.py`, called by `apply.py`). A ticked Resume starts a Claude thread through `orca agent launch --agent claude --worktree id:<repoId>::<path> --prompt "<the handoff's own next command>" --json`, one at a time, at most 3 per run. The prompt is the last slash-command line in the newest handoff file that names the worktree (for example `/to-driver <handoff path>`); a handoff with no such line gets `/to-driver <handoff path>`. A row beyond 3, a worktree Orca cannot target, a worktree whose Orca card was active in the last 24 hours, and a failed launch each write a done bubble with the same command to `<dir>/dones.json` and start nothing. Success needs `ok` and `prompt.outcome` of `journaled` or `handed-to-terminal`; the result round lists every thread started with its receipt.
7c. **Post the asks and done bubbles.** For each entry in `<dir>/dones.json`, run `~/.claude/bin/xagent-ask --done --note <note> --copy <copy>` (plain, it does not wait). For each entry in `<dir>/asks.json`, run `~/.claude/bin/xagent-ask --question <question> --choice <c> ...` with `run_in_background`. The answer 'Re-check and apply now' means `apply.py <dir> <responses.json> --only <row key> --reapply`; a ticked box chosen from a two-tick ask means `--only <row key> --choose "<option>"`. 'Leave it' means do nothing.
7d. **Deliver round two.** Stop the earlier listener (`pkill -f "brief-deliver <dir>/cleanup.html"`), then start `~/.claude/bin/brief-deliver <dir>/cleanup.html` in the background. Give the `file://` link.
8. **Sign off.** `python3 REG sign-off cleanup:run --status done --note "<counts per group>"`.

## `/cleanup --scheduled`

The weekly automation's prompt. The same run as `/cleanup`, with one change at step 1: take the claim with `python3 <skill-dir>/schedule.py gate` instead. Exit 0 means claimed, go on. Any other exit means another live session holds `cleanup:run` (or this thread has no identity): print its one line and stop, with no brief and no other output. **Failure path: every exit after a successful gate, on any error, timeout or stop, first runs `python3 REG sign-off cleanup:run --status incomplete --note "<why>"`, so a failed run never holds the claim.** If the gate says the claim is held for over 7 days, it prints the holder's age and posts an Agent X bubble; the owner releases it with `python3 REG clear <thread>`. The run then discovers, auto-prunes, delivers the brief and waits for Save. It pushes, merges, deletes and starts nothing until the brief comes back.

## `/cleanup schedule` and `/cleanup unschedule`

Run `python3 <skill-dir>/schedule.py schedule` and report its one line (the automation id). It makes the folder `~/.claude/cleanup/scheduled/` and registers it with Orca as a folder project when it is not yet, then runs `orca automations create` with `--trigger weekly --day 1 --time 08:00 --timezone Australia/Brisbane --provider claude --workspace path:<that folder> --prompt "/cleanup --scheduled"`. It never passes `--repo`, which would make a fresh worktree on every run for cleanup to classify. That folder is classified Skipped and never pruned. A second `schedule` reports the existing id and creates nothing. It only ever treats as its own an automation whose id it saved in `~/.claude/cleanup/schedule.json` or whose prompt is `/cleanup --scheduled` in that folder; a same-named automation that is not that is refused with one line and never removed. `python3 <skill-dir>/schedule.py unschedule` removes the automation by id.

## The brief

`brief-id: cleanup-<run-id>`, so last week's ticks never repaint this week's brief, and every row key carries the tip SHA (`wt-<repo>-<name>-<sha7>`, `push-<repo>-<sha7>`).

Answers block (the four group counts), the verdict line (what sending it back untouched approves), then four parts: **Running** (table from the conductor's claims), **Pruned** (table of what was actually removed, naming each Orca card closed), **Ready to push** (one question per repo listing every commit), **Looks abandoned** (one question per worktree: For you, What the change does, How far it got, Why it stopped, what each road costs, the diff in a collapsed block).

Each decision row is a tick-box group pre-ticked by pre-filling its hidden `textarea[data-note]` with the recommendation; a hand-written `checked` is ignored by the runtime. An emptied group exports `none` (peakstate-brief runtime), which means "do nothing this run".

| Row | Options | Recommended |
| --- | --- | --- |
| Push (per repo) | Push now · Push when the running work lands · Hold, ask me again next cleanup | Hold when any claim in the repo is `waiting-on-user` or `blocked`; else Push when the running work lands when another worktree in the repo is Running; else Push now. |
| Abandoned | Resume from its handoff (only with a handoff) · Merge and push (only a branch with commits) · Park for 30 days · Delete (not detached, nested or unreadable) | The subagent's pick, checked by `make_brief.py`: Delete only when no commit is lost, Resume only with a handoff; otherwise Park. |

## `/cleanup --discover-only`

Run `python3 <skill-dir>/discover.py --discover-only --report`. It lists each group (Running, Pruned, Ready, Abandoned, Parked, Landing, Skipped, Main) with its count and the reason per worktree, then the push rows. Report the counts, the repos with a push row and any fetch failure. Stop.

## Discovery, in short

Liveness (a conductor session whose transcript's latest `cwd` is inside, a process working directory inside, Orca activity, an open or held claim) blocks every prune; transcripts are read by a bounded tail seek, never loaded. `discover.py` skips `~/Library`, `~/.Trash`, `~/.claude/plugins`, `node_modules`, `.next`, venvs, `dist`, `build`, `.cache` and hidden folders other than `~/.claude`, with a depth cap of 5. An optional private `~/.claude/cleanup.json` adds `{"exclude": [...], "extra_roots": [...]}`. Worktrees outside the walk are found through `git worktree list --porcelain` of their main repo.
